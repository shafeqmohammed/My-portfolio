01 — Overview

Infrastructure people can operate with confidence

Bridge is Armada’s GPU-as-a-Service experience. Teams use it to get GPU compute for AI workloads: connect to the service, choose and configure capacity, run and monitor workloads, and recover when something goes wrong.

The design challenge was not drawing a console. It was translating a deeply technical system — hardware classes, capacity, provisioning, usage and failure — into a sequence of decisions that people can understand and trust.

02 — The problem

The system’s structure is not the user’s mental model

Infrastructure products tend to expose their own architecture: clusters, nodes, quotas, logs. The people using them think in workloads, deadlines and budgets. That gap shows up as hesitation during configuration, uncertainty about what a workload is doing, and support requests when a state is unclear.

Three questions had to be answerable at every point: What is happening right now? What needs my attention? What happens if I take this action?

04 — What made it difficult

Constraints that shaped the design

01Capacity changes in real time. What is available when a user starts configuring may not be available when they confirm.
02Long-running, asynchronous states. Provisioning and workloads run for minutes to days; the interface has to stay truthful the whole time.
03Cost and consequence. Configuration choices carry real cost, so uncertainty at the moment of commitment is expensive.
04Different expertise levels. Infrastructure specialists and model builders use the same product with very different vocabularies.
05 — Key decisions

Four decisions that simplified the product

01

Organise around the workload, not the hardware

The workload became the primary object. Hardware, capacity and usage are attributes of a workload rather than separate places to navigate.

Trade-off: specialists lose a hardware-first view, so it remains available as a secondary lens.

02

One state model, everywhere

Every workload uses the same small set of states, with the same names, colours, icons and next actions in lists, detail views and notifications.

Trade-off: some engineering sub-states are grouped, with detail one level down.

03

Show trade-offs at the moment of choice

Availability, expected wait and estimated cost sit beside each option before the user commits, instead of appearing after the fact.

Trade-off: estimates need clear labelling so they are not read as guarantees.

04

Make every failure recoverable

Each error state says what happened, why it matters and the next best action — retry, change configuration or contact support — rather than only reporting a code.

Trade-off: requires close work with engineering to map failure causes to actions.
